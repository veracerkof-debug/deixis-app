## 1. Критично

### К1. Токены сопряжения и токен оператора лежат в файлах без ограничения прав

**Где:**
- `desktop/src/main/kotlin/app/deixis/desktop/ReceiverApp.kt:136` — `Pairing(FileTokenStore(File(opts.dataDir, "tokens.json")))`
- `desktop/src/main/kotlin/app/deixis/desktop/ReceiverApp.kt:516-520` — `file.writeText(token)` для `operator-token`
- `core/src/main/kotlin/app/deixis/core/Pairing.kt:146-154` — `FileTokenStore.save()` пишет через `writeText`

**Что не так.** Папка данных на компьютере — `~/.deixis/receiver` (`Main.kt:43,51`). Файлы `tokens.json`
и `operator-token` создаются с правами по умолчанию (обычно `0644`), а сама папка — `0755`. При этом
**приватный ключ TLS, лежащий рядом, защищён** явно:

```kotlin
// core/src/main/kotlin/app/deixis/core/Tls.kt:85
runCatching { keyFile.setReadable(false, false); keyFile.setReadable(true, true) }
```

То есть ключ закрыт, а ключи от экрана — нет. На общем компьютере (класс, аренда, офис) любой локальный
пользователь читает `tokens.json` и получает пульт от экрана, а из `operator-token` — пульт **оператора**:
с правом подтверждать и отклонять подключения и отключать других пультов (`Peers.kt:94`, команда `Kick`
в `Receiver.kt:550`).

**Как исправить.** Тот же приём, что в `Tls.kt`, применить к обоим файлам:

```kotlin
// core/src/main/kotlin/app/deixis/core/Pairing.kt — в save() после rename
runCatching { file.setReadable(false, false); file.setReadable(true, true) }

// desktop/.../ReceiverApp.kt:519 — после writeText
runCatching { file.setReadable(false, false); file.setReadable(true, true) }
```

На Windows POSIX-прав не нужно (папка `%APPDATA%` и так своя у пользователя), на Linux/macOS — обязательно.
Заодно стоит закрыть `~/.deixis/receiver` целиком (`setReadable(false, false)` на каталог) и
`sender-tokens.json` (`Main.kt:67`).

**Оценка:** правка на 6 строк, риск нулевой, а снимает реальную возможность «захватить показ» с того
же компьютера.

### К2. Драйвер: гонка при подключении монитора и риск создать два монитора

**Где:** `windows-display/driver/DeixisDisplay.cpp:346-388` (`ConnectMonitor`), `:225` (`g_parseModes`),
`:329-343` (`DeixisAdapterInitFinished`).

**Что не так.** `ConnectMonitor` вызывается из обработчика `DeixisAdapterInitFinished` **и** из
запасного потока (`CreateThread` + `Sleep(1000)`, строки 336-341) — без общей блокировки:

```cpp
static bool ConnectMonitor(IDDCX_ADAPTER adapter) {
    for (const Variant& v : variants) {
        g_parseModes = v.modes;          // ← пишется здесь
        ...
        IddCxMonitorCreate(...);          // ← Windows может уже читать g_parseModes
```

`g_parseModes` — глобальная переменная, и она же читается в `DeixisParseMonitorDescription`
(строка 396) из потока Windows. Между «проверили `MonitorModeBufferInputCount < count`» и
`FillMonitorModes(in->pMonitorModes, true, count)` значение может смениться на другое
(1 режим вместо 3) → Windows запишет в буфер меньше, чем ожидает, либо получит рассогласованный
`MonitorModeBufferOutputCount`.

Вторая проблема того же места: если первый вызов `ConnectMonitor` уже создал монитор, а затем
сработал запасной поток — будет создан **второй монитор**, а `g_monitor` (строка 227) просто
перезапишется, и первый объект останется жить без ссылки.

**Как исправить.**

1. Ввести флаг подключения под тем же `g_lock`, что уже есть в файле:

```cpp
bool g_connected = false;   // рядом с g_monitor
```

и в начале `ConnectMonitor` под `AcquireSRWLockExclusive(&g_lock)`:

```cpp
if (g_connected) return true;
```

2. Защитить `g_parseModes` тем же замком и брать копию под замком:

```cpp
UINT modes;
AcquireSRWLockExclusive(&g_lock);
modes = g_parseModes;
ReleaseSRWLockExclusive(&g_lock);
```

3. Убрать запасной поток или сделать его единственным путём (сейчас он дублирует первый вызов).
Самый простой вариант — оставить только поток, но тогда `g_parseModes` пишется и читается
из одного места.

**Оценка:** в CI драйвер проверяется на настоящей Windows, но гонка проявится не всегда — это
классический «иногда виснет на одном компьютере» баг. Правка — около 20 строк.

### К3. Драйвер: режим «без EDID» объявлен как EDID с нулевым размером

**Где:** `windows-display/driver/DeixisDisplay.cpp:364-366`.

```cpp
info.MonitorDescription.Type = IDDCX_MONITOR_DESCRIPTION_TYPE_EDID;
info.MonitorDescription.DataSize = v.edid ? sizeof(kEdid.data) : 0;
info.MonitorDescription.pData = v.edid ? const_cast<BYTE*>(kEdid.data) : nullptr;
```

Для варианта `{false, kModeCount, ...}` (строка 354) тип остаётся `EDID`, но данных нет и размер ноль.
Это противоречие: система получает «здесь EDID» и «EDID нулевой длины». Вариант «монитор без EDID»
(а он в списке вариантов не зря) может отвергаться именно из-за этого.

**Как исправить.** Для варианта без EDID ставить честный тип:

```cpp
if (v.edid) {
    info.MonitorDescription.Type = IDDCX_MONITOR_DESCRIPTION_TYPE_EDID;
    info.MonitorDescription.DataSize = sizeof(kEdid.data);
    info.MonitorDescription.pData = const_cast<BYTE*>(kEdid.data);
} else {
    info.MonitorDescription.Type = IDDCX_MONITOR_DESCRIPTION_TYPE_OTHER;
    info.MonitorDescription.DataSize = 0;
    info.MonitorDescription.pData = nullptr;
}
```

**Оценка:** 6 строк, снимает целый класс отказов «Windows не увидела монитор».

### К4. Токены сопряжения бессрочны

**Где:** `core/src/main/kotlin/app/deixis/core/Pairing.kt:101-108` (поле `pairedAt` есть), `:131-155`
(`FileTokenStore` хранит токены, срока жизни нет), `forget()` вызывается только при `Kick`
(`Peers.kt:98`) и при неудачном подтверждении оператором.

**Что не так.** PIN меняется при каждом успешном сопряжении, а вот выданный токен — нет. Поле
`pairedAt` записывается и **нигде не читается**. Токен, утёкший хоть раз (см. С1 — он ходит в URL `?t=`
и живёт в cookie год), даёт доступ к показу навсегда: показывать слайды, гонять видео, отключать
другие пульты.

**Как исправить.** Добавить в `Pairing` срок жизни и чистку по нему:

```kotlin
// рядом с isValid()
fun isValid(token: String?, secure: Boolean = false): Boolean {
    ...
    if (now - s.pairedAt > TOKEN_TTL_MS) { tokens.remove(s.token); return false }
    ...
}
```

`TOKEN_TTL_MS` — например 90 дней (пульт телефона подключается почти каждый день; 90 дней — с запасом).
Плюс кнопка «Забыть все сопряжения» в настройках приёмника — сейчас можно отключить только конкретный
пульт через `Kick`.

### К5. Сборка падает на любой машине без UTF-8 локали

**Где:** `android/phone/src/main/assets/demo/` — восемь файлов с русскими именами
(`Город пятнадцати минут.pdf`, `Огни. Видеофон.mp4`, `Лекция. Город 15 минут.pptx` и другие).
Задача, которая их перечисляет: `desktop/build.gradle.kts` → `writeDemoIndex`
(`inputs.dir(demoAssets.resolve("demo"))`).

**Что не так.** Это воспроизвелось на моей машине — и это не «теория»:

```
> Task :desktop:writeDemoIndex FAILED
> Failed to create MD5 hash for file
> '.../assets/demo/?????????? ???????????????????? ??????????.pdf'
> as it does not exist.
```

Причина: JVM читает имена файлов в кодировке `sun.jnu.encoding`, а она берётся из локали ОС.
На машине с `LANG=` (пусто) и `LC_CTYPE=POSIX` получается `ANSI_X3.4-1968`, и кириллица
превращается в `????` — Gradle считает, что такого файла нет.

Проверено отдельно: `-Dsun.jnu.encoding=UTF-8` **не помогает** — JVM всё равно остаётся
на `ANSI_X3.4-1968` (свойство только читается из локали, из командной строки не меняется).

Где локаль сейчас задана явно — только в двух местах:
`core/build.gradle.kts:42-43` (для тестов) и `desktop-smoke.yml:158` (для одного Linux-шага).
Все остальные задания CI и все сборки на машине разработчика полагаются на локаль по умолчанию.
На runner'ах GitHub `LANG=C.UTF-8` есть, поэтому CI зелёный — но это luck, а не правило.

Затронуты: `ci.yml` (задание core-desktop), `smoke.yml`, `release.yml`, `ui-shots.yml`,
`desktop-smoke.yml` (шаг сборки) и любая локальная сборка в Docker-образе без UTF-8 локали
(минимальные образы, `LANG=POSIX` в некоторых корпоративных окружениях).

**Как исправить.** Два шага, первый обязательный, второй по вкусу.

*Шаг 1 — понятная ошибка вместо загадочной.* В корневом `build.gradle.kts`:

```kotlin
// Имена файлов читаются в кодировке локали: без UTF-8 кириллические имена не видны,
// и сборка падает позже, с невнятной ошибкой про хэш файла.
val jnu = System.getProperty("sun.jnu.encoding").orEmpty()
if (jnu.isNotEmpty() && !jnu.startsWith("UTF", ignoreCase = true)) {
    throw GradleException(
        "Кодировка имён файлов: $jnu. В проекте есть файлы с русскими именами — " +
        "запустите сборку в UTF-8 локали: LC_ALL=C.UTF-8 LANG=C.UTF-8 ./gradlew ..."
    )
}
```

*Шаг 2 — задать локаль в CI явно*, во всех workflow, где идёт сборка
(`ci.yml`, `smoke.yml`, `release.yml`, `ui-shots.yml`, `desktop-smoke.yml`):

```yaml
env:
  LC_ALL: C.UTF-8
  LANG: C.UTF-8
```

*Шаг 3 (по желанию, «пуленепробиваемый» вариант) — переименовать демо-файлы в ASCII* и хранить
русские названия отдельно. Сейчас имя файла **и есть** заголовок в демо
(`pult/.../Controller.kt:1403`: `it.copy(title = name.substringBeforeLast('.'))`), поэтому понадобится
маленький манифест «файл → заголовок». Зато сборка перестанет зависеть от локали совсем.

## 2. Существенно

### С1. Токен веб-пульта всё ещё ходит в URL, а cookie живёт год

**Где:** `core/src/main/kotlin/app/deixis/core/WebRemote.kt:466`
(`core.pairing.isValid(request.queryParameters["t"])`), `:560-561` (`REMOTE_COOKIE_AGE_S = 365 * 24 * 60 * 60`).

`Referrer-Policy: no-referrer` на странице уже стоит (`WebRemote.kt:290`) — от утечки через Referer
защитили. Но токен в адресе остаётся в: истории браузера, журналах сервера приёмника (Ktor пишет URL
запроса), буфере обмена при копировании ссылки на файл, и в скриншотах. Постоянный токен в cookie
сроком в год — это тот же токен, что и в `tokens.json` (К1), только в другом месте.

Сверх того, веб-пульт **кладёт токен в `localStorage` навсегда** (`core/src/main/resources/web/remote.html:900-908`:
`store.set("token", token)`), а при первом входе принимает его из `location.hash`
(`remote.html:907`). Фрагмент не уходит на сервер — это правильно, — но он остаётся в адресной строке
и в истории. В сочетании с бессрочным токеном (К4) получается, что один раз открытый веб-пульт
на компьютере оператора годами держит в браузере действующий ключ от экрана.

**Как исправить.** Короткоживущая подписанная ссылка вместо самого токена:

- на приёмнике — HMAC-SHA256 от `(sha файла, issuedAt)` секретом приёмника;
- страница пульта просит `/remote/file/{sha}?exp=…&sig=…`;
- приёмник проверяет подпись и срок (5-10 минут), а не сравнивает токен;
- cookie сеанса — сократить до 1-8 часов, а не год (год нужен только для «пульт открыт постоянно»,
  этого достаточно и с переподключением).

### С2. В CI — инъекция входных данных в команду

**Где:** `.github/workflows/ui-shots.yml:33`

```yaml
script: ./tools/android-shots.sh ${{ github.event.inputs.extra }}
```

`extra` — свободный текст из `workflow_dispatch`. Он подставляется прямо в строку команды. Кто может
запустить workflow вручную (а это, при `contents: write`, заметная сила), получает выполнение
произвольной команды в контексте CI с токеном репозитория. Классическая script injection в Actions.

**Как исправить.** Передать через окружение, а не через подстановку в команду:

```yaml
- name: Снимки
  uses: reactivecircus/android-emulator-runner@v2
  env:
    EXTRA: ${{ inputs.extra }}
  with:
    script: ./tools/android-shots.sh
```

и разбирать `EXTRA` внутри скрипта как данные (не как команду).

### С3. `permissions: contents: write` на уровне workflow

**Где:** `.github/workflows/release.yml:22`, `.github/workflows/ui-shots.yml:24`.

Права на запись в репозиторий получает **каждое** задание workflow, включая сборку APK, сборку
установщиков и эмуляторные прогоны. Достаточно указать права на уровне конкретных заданий —
у `release` (создание релиза) и у шага публикации снимков.

**Как исправить.** Убрать workflow-level `permissions`, в нужных заданиях:

```yaml
jobs:
  release:
    permissions:
      contents: write
```

### С4. Actions закреплены тегами, а не SHA

**Где:** все workflow — `actions/checkout@v5`, `actions/setup-java@v5`, `gradle/actions/setup-gradle@v4`,
`actions/upload-artifact@v4`, `softprops/action-gh-release@v2`, `reactivecircus/android-emulator-runner@v2`.

Тег можно перенаправить: владелец actions (или взлом аккаунта) меняет `v5` на вредоносный коммит —
и код выполняется в CI с доступом к секретам и токену репозитория. Для проекта, который собирает
и подписывает APK вашим ключом, это заметный риск цепочки поставки.

**Как исправить.** Закрепить SHA и обновлять через Dependabot:

```yaml
- uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608 # v5.0.0
```

`dependabot.yml` с `package-ecosystem: github-actions` обновит их автоматически.

### С5. В репозитории лежит артефакт сборки

**Где:** `tools/__pycache__/ui_names.cpython-313.pyc` — в индексе git.

### С6. Демо грузит скрипты с чужого CDN

### С7. У загрузок из браузера нет ни общего лимита, ни лимита на число одновременных

**Где:** `core/src/main/kotlin/app/deixis/core/WebRemote.kt:62-89` (`UploadArea`), `:316-333`
(маршрут `PUT /remote/upload/{id}`), `core/src/main/kotlin/app/deixis/core/FileStore.kt:106-121`
(`ensureSpace`).

Ограничения есть: один файл — не больше 1 ГБ (`FILE_LIMIT_BYTES`), файл не больше кэша в 10 ГБ,
на экране показываемое не вытесняется. Но:

- квота 10 ГБ считается **только по файлам верхнего уровня** (`FileStore.kt:114` —
  `dir.listFiles()?.filter { it.isFile }`), а незаконченные загрузки лежат в подпапке `uploads/` и
  в расчёт не входят вообще;
- число одновременных загрузок не ограничено: `writing` в `UploadArea` — это множество занятых
  `id`, а не счётчик (`WebRemote.kt:56`), то есть хоть сто параллельных загрузок по 1 ГБ;
- брошенные `.part` живут до `FILE_TTL_MS` = 24 часов (`Receiver.kt:622`).

Итог: пульт с действительным токеном (или украденным токеном из С1) может забить диск приёмника
(у ТВ и приставки он обычно маленький) и положить показ — то есть ровно то, чего правило CLAUDE.md
запрещает («сбой пульта не трогает вывод»).

**Как исправить.**

- общий лимит на папку `uploads/` (например 2 ГБ) и счётчик одновременных загрузок
  (`MAX_UPLOADS = 4`), с отказом `429`/`507`;
- включить `uploads/` в подсчёт занятого места в `ensureSpace` — одной строкой:

```kotlin
var used = dir.listFiles()?.sumOf { if (it.isFile) it.length() else it.walkBottom().filter(File::isFile).sumOf(File::length) } ?: 0
```

- чистить `.part` по времени и по размеру, а не только по TTL.

### С8. `android/receiver` — 2 140 строк без единого модульного теста

**Где:** `android/receiver/src/main/kotlin/app/deixis/receiver/` — `SlideBitmap.kt`, `SlideCanvas.kt`,
`ScreenDecoder.kt`, `VlcPlayer.kt`, `OverlayLayer.kt`, `PptxPdf.kt`, `ReceiverScreen.kt`.

Это код, который рисует **в зал**: слайды, PDF, декодирование видеопотока, слой наложения. Своей
тестовой папки у модуля нет, а тесты `android/phone` (6 файлов) код приёмника не трогают
(проверено grep'ом). Единственная проверка — эмулятор в CI, где одна ошибка раскладки видна только
на глаз.

При этом в `desktop` лежит почти такой же рендер (`SlideRenderer.kt`) — и он покрыт тестами
(`SlideRendererTest.kt`, `AspectDesktopTest.kt`).

**Как исправить.** Два пути, по возрастанию трудоёмкости:

1. **Быстрый:** вынести чистые части приёмника (расчёт пропорций, раскладка слайда, разбор PDF
   в картинку) в `core`/`desktop`, где для них уже есть тестовая база; в `android/receiver`
   останется только платформенный код.
2. **Правильный:** добавить `android/receiver/src/test` с тестами на `SlideBitmap`/`SlideCanvas`
   и на `ScreenDecoder` (используя `android.jar` из SDK и `Robolectric`-подобный подход либо
   выделив логику в чистые Kotlin-классы).

Минимум, который даст пользу сразу: тест на `Aspect`/`SlideCanvas` в `core`, если вынести туда
расчёт пропорций (часть логики уже дублируется с `desktop`).

### С9. `pult` — не модуль Gradle, а папка с исходниками

**Где:** `pult/src/main/kotlin/app/deixis/phone/` (32 файла, 10 640 строк), подключается так:

```kotlin
// desktop/build.gradle.kts
kotlin.sourceSets["main"].kotlin.srcDir("../pult/src/main/kotlin")
// android/phone/build.gradle.kts
sourceSets["main"].java.srcDir("../../pult/src/main/kotlin")
```

Следствия: нельзя собрать и протестировать `pult` отдельно; его тесты живут в двух чужих модулях
(`android/phone/src/test`, `desktop/src/test`); папка называется `pult`, а пакет внутри — `app.deixis.phone`;
при сборке `pult` компилируется дважды (в APK и в desktop-дистрибутив), что не видно по структуре проекта.

**Как исправить.** Сделать настоящий модуль `:pult` с `api(project(":core"))`, а `desktop` и
`android/phone` — зависимыми от него. Тогда у `pult` появятся свои тесты, а правка общей кода
перестанет ломать две сборки сразу. Если это не хочется — хотя бы описать устройство в
`ARCHITECTURE.md` и добавить в CI проверку, что в `pult` нет Android-зависимостей
(сейчас это держится только на честном слове).

## 3. Умеренно

### У1. Ненужное разрешение `CHANGE_NETWORK_STATE`

`android/phone/src/main/AndroidManifest.xml:14`. Приложение не переключает сети — оно их использует.
Разрешение лишнее и выглядит неопрятно в списке разрешений. Убрать (проверить, что `jmdns`/multicast
не требуют его на API 26+; для многоадресной рассылки нужен `WifiLock`, а не это разрешение).

### У2. `usesCleartextTraffic="true"` на весь телефон

`android/phone/src/main/AndroidManifest.xml:31`. Приложение по сути работает в локальной сети, но флаг
разрешает открытый HTTP **везде**, включая интернет. `networkSecurityConfig` не умеет «только локальная
сеть» (там только домены), так что полностью убрать нельзя. Компромисс, который стоит сделать:
оставить флаг, но добавить в `res/xml/network_security_config.xml` `cleartextTrafficPermitted="false"`
по умолчанию и точечное исключение — тогда случайная утечка HTTP наружу станет заметной в логах.

### У3. `Conversions.done` растёт без ограничения

`core/src/main/kotlin/app/deixis/core/Convert.kt:101` — карта переведённых файлов на весь сеанс.
Переводов обычно десятки, но при долгой работе и смене файлов память растёт. Достаточно
`LinkedHashMap` с ограничением в ~50 записей (вытеснять самый старый).

### У4. Чистка файлов обновления — по префиксу имени

`core/src/main/kotlin/app/deixis/core/Updates.kt:326`:
`dir.listFiles()?.filter { it.name.startsWith("update-") && !it.name.endsWith(".json") }`.
Любой будущий файл с префиксом `update-` будет молча удалён. Лучше держать в отдельной подпапке
`updates/files/` и чистить её целиком.

### У5. Путь к скрипту в `sh -c` не экранирован

`desktop/src/main/kotlin/app/deixis/desktop/DesktopUpdates.kt:114`:

```kotlin
ProcessBuilder("/bin/sh", "-c", "nohup /bin/sh '${script.absolutePath}' >/dev/null 2>&1 &").start()
```

Одинарная кавычка в пути (например, в имени папки пользователя) закроет строку и даст инъекцию.
Путь лежит в домашней папке, так что это маловероятно, но правится одной строкой: заменить
`'${...}'` на `"${...}"` или на `ProcessBuilder("/bin/sh", script.absolutePath)` без `-c`.

### У6. Путь к `.msi` подставляется в `.cmd` без экранирования

`desktop/src/main/kotlin/app/deixis/desktop/DesktopUpdates.kt:~125` (`windowsScript`): путь вставляется
в batch-файл как `"${msi.path}"`. Символы `%` и `"` в пути сломают скрипт (а `&` — выполнение команды).
Сейчас путь формируется из имени файла выпуска, то есть под контролем автора репозитория, — риск
низкий, но экранирование `^` и `%` стоит сделать.

### У7. `Pairing.trimAttempts` может вытеснить ту же запись, которую только что добавили

`core/src/main/kotlin/app/deixis/core/Pairing.kt:37` и `:58-60`: `getOrPut(...)` добавляет адрес, и
`trimAttempts()` (лимит 256) удаляет самую старую запись — это может оказаться только что добавленный
адрес. Тогда следующая попытка не попадёт в счётчик. Мелочь, но легко чинится: сначала обрезать,
потом добавлять.

### У8. `docs/audit/REPORT.md` устарел

Отчёт описывает состояние на 0.10.22, сейчас в `CHANGELOG.md` — 0.10.32. Часть открытых пунктов
закрыта (TLS, пауза PIN по адресу, cookie сеанса, переводы, «Чёрный экран», чтение библиотеки по
частям). Актуализировать статус: иначе следующий проход будет тратить время на уже сделанное.

### У9. «Большие» файлы `pult/Controller.kt` (1 865 строк) и `core/Ppt.kt` (1 186)

`Controller.kt` держит состояние пульта, сети, показа и профилей. Разделение по «источникам данных»
(state + отдельные редьюсеры) уменьшит риск и облегчит тесты. Не срочно: код рабочий и покрыт
косвенно тестами `android/phone` и `desktop`.

### У10. Отсутствие статического анализа и контроля зависимостей

В проекте нет `detekt`/`ktlint`, нет `dependencyVerification` в Gradle, нет проверки лицензий зависимостей
в CI (лицензии перечислены в `NOTICE` вручную). Три конкретных шага:

- `dependencyVerification { verify(...) }` в `gradle/verification-metadata.xml` — защита от подмены
  артефактов в Maven Central (имеет смысл, так как сборка тянет ~30 зависимостей);
- `detekt` с базовым набором правил — ловит «пустой catch», `!!`, длинные функции, `Thread.sleep` в UI;
- проверка лицензий (`org.licensee` или `licensee` CLI) в CI — чтобы новый `implementation(...)` не
  принёс несовместимую лицензию молча. Сейчас это держится только на внимании автора.
