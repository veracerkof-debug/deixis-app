# Как работать над Deixis

Правила для человека и для ИИ, который продолжает работу. Жёсткие правила продукта — в
[../../CLAUDE.md](../../CLAUDE.md); здесь они расписаны подробно, вместе с порядком работы.

## 1. Роли

- **Автор** — идеолог продукта. Пишет по-русски, решает, *что* делать и *зачем*, проверяет на своих устройствах
  (Windows, Linux Mint, телефон, ТВ). В технических решениях полагается на исполнителя: тот выбирает *как*, сам
  перепроверяет и отвечает за стабильность.
- **Исполнитель** (программист или ИИ) — делает, проверяет, выпускает и коротко отчитывается по-русски:
  что сделано, что проверено, что не проверено и почему.

Короткие команды автора:
- «Работай» / «Работать» — начинать сейчас, не дожидаясь назначенного времени.
- «Кидай» / «кидай в мейн» — отправить в основную ветку сейчас.

## 2. Жёсткие правила продукта (подробно)

| Правило | Что значит на практике | Где проверяется |
|---|---|---|
| На вывод в зал не попадает интерфейс | Тосты, ошибки, курсор, системные панели, PIN — не в зале. Исключение: заставка с QR и PIN, когда показывать нечего или оператор сам нажал «QR и код на экран» (`connectCard`) | `OutputWindow`, `ReceiverScreen`, GUI-тесты |
| Сбой пульта не трогает вывод | Нет нового слайда — остаётся прежний или чёрный. Ошибка кадра — чёрный кадр и сообщение пульту (`reportError`) | `OutputWindow.redraw`, `PdfSlide` |
| Цвета, размеры, анимации — только из токенов | В коде интерфейса нет чисел: `T.*`, палитры `P`, `OutputTokens`, `WindowTokens` | ревью; `pult/…/Theme.kt` |
| Все строки — RU (основной), UZ латиницей, EN | Пульт: `L` в `pult/…/Strings.kt` через `t(ru, uz, en)`; окна компьютера: `desktop/…/Words.kt`; веб-пульт: словарь в `remote.html`. Без «ты»/«вы» | `StringsTest` (ищет русские строки вне словаря) |
| Без рекламы, аналитики, трекеров; сеть только по действию оператора | Никаких фоновых отправок; журнал уходит только кнопкой «Отправить» | ревью |
| Новый жест — в карту жестов `DESIGN.md` | Клавиши компьютера — тоже там | ревью |
| Значимое решение — строкой в `DECISIONS.md` | Сверху, с датой, «почему» — словами автора, если есть | ревью |
| Лицензии | Проект GPL-3.0-or-later. Библиотеки только Apache-2.0, MIT, BSD, MPL-2.0, LGPL. Чужой код приложений не копируется (исключение — AirPlay по UxPlay, см. `NOTICE`). Закрытые SDK — только во flavour для Google Play | `NOTICE`, ревью |

## 3. Ветки, коммиты, отправка

- Основная ветка — `ccr-7f6c4278-1t09zq`; ветки `main` нет. «В мейн» — значит в неё.
- Pull request не создаются, если автор не попросил.
- Сообщение коммита — по-русски: первая строка — что изменилось для людей, дальше — причина и подробности.
  В конце — строки соавторства, которые задаёт среда разработки. Идентификаторы моделей ИИ в репозиторий
  не пишутся.
- Ключи, пароли и почту в репозиторий не класть. Секреты подписи — только в настройках GitHub (`DEIXIS_KEYSTORE*`).
- Закончил работу → коммит → короткое сообщение автору. Если автор за 5 минут ничего не добавил — отправить
  в основную ветку. Проверка сеанса может требовать отправки сразу: тогда отправить и сказать об этом.

## 4. Перед отправкой — проверить самому

```sh
export LC_ALL=C.UTF-8            # кириллица в именах файлов тестов
./gradlew :diag:test :core:test :desktop:test
ANDROID_HOME=/opt/android-sdk ./gradlew :android:phone:testDebugUnitTest :android:receiver:testDebugUnitTest
# окна (Linux):
xvfb-run -a -s "-screen 0 1600x1000x24" ./gradlew :desktop:test -Ddeixis.gui=1 --tests '*DesktopWindowTest*' --tests '*PultWindowTest*'
```
Подробно — [BUILD_TEST_RELEASE.md](BUILD_TEST_RELEASE.md). Что нельзя проверить локально (Android на
эмуляторе, Windows, macOS), проверяет CI. Не заявлять «проверено», пока CI не зелёный.

## 5. После отправки — довести до выпуска

1. Дождаться: `CI`, `Android smoke`, `Запуск программы для компьютера` (desktop-smoke), `Снимки интерфейса`,
   при правке драйвера — `Виртуальный монитор Windows`.
2. Красное — разобрать по логу задания и исправить. «Нестабильный тест» — не причина. Тесты не отключать.
3. Всё зелёное — выпуск: workflow `release.yml` с входами `version` (например `0.10.34`) и `publish: true`,
   затем `demo.yml`.
4. Проверить публикацию:
   `curl -sSL https://github.com/veracerkof-debug/deixis-app/releases/latest/download/release.json`.
5. Сообщить автору ссылки: `.msi` (Windows), `.deb` (Linux), `.dmg` (Мак), APK телефона и ТВ (`-all.apk`).
6. В `CHANGELOG.md` раздел версии пишется **до** выпуска: из него берётся текст «Что нового».

## 6. Как разговаривать с автором

- Коротко и по делу, по-русски, без технического жаргона там, где можно сказать проще.
- Всегда отделять «проверено» от «не проверено» и говорить, на чём проверено (CI на Windows, эмулятор,
  локально на Xorg-заглушке…).
- Нужен журнал с устройства автора — просить конкретно: «Настройки» → «Диагностика» → «Отправить файлом».
- Если работа отложена («на среду»), записать её полный текст в напоминание, чтобы она не зависела от памяти.

## 7. Документация — часть работы

Изменение поведения без обновления документов не закончено:
- `CHANGELOG.md` — для людей, по версиям;
- `DECISIONS.md` — значимые решения;
- `ARCHITECTURE.md`, `SCREENS.md`, `DESIGN.md` — если меняется устройство, экраны, дизайн;
- `docs/dev/*` — если меняется то, что там описано; новые разборы сбоев — в
  [KNOWLEDGE.md](KNOWLEDGE.md).

## 8. Начало и конец сессии

Правило автора: весь контекст — в документации проекта; после законченной сессии беседа очищается.

**Начало.** Прочитать [STATUS.md](STATUS.md) (что ждём, что дальше), затем нужные разделы по
[../README.md](../README.md). Не опираться на память прошлых бесед — её нет.

**Конец** (до очистки беседы):
1. [STATUS.md](STATUS.md) — переписать: ждём от автора, следующие шаги по приоритету, что сделано, дата и версия.
2. [KNOWLEDGE.md](KNOWLEDGE.md) — каждая найденная причина сбоя, обходной приём, «почему так».
3. `DECISIONS.md` — решения; `CHANGELOG.md` — изменения; остальные `docs/` — если изменилось устройство.
4. Отложенные задачи — в STATUS.md («Следующие шаги»), а не только в напоминания.
5. Коммит, отправка в основную ветку. Сообщить автору, что сессию можно очищать.
6. Проверка перед «можно очищать»: нет ли в беседе знания, которого нет в документах (решение автора, причина, договорённость, открытый вопрос). Есть — записать и отправить заново.

Правило действует после **каждой** законченной работы, а не только после большой: чем короче беседа, тем меньше
токенов она тратит. Очистку (`/clear`) делает автор, ИИ о ней напоминает.
