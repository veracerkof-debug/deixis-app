# Викторины и интерактивные уроки (план)

**Статус: сделан шаг 1 и модель шага 2** (формат, проверка, проверка ответов, самостоятельное прохождение — в `core/.../quiz/`, 14 тестов). Плеера с экраном, редактора и живой игры пока нет. Решения приняты 2026-11-13 (см. [../../DECISIONS.md](../../DECISIONS.md)). Когда
появится код — этот документ превращается из плана в описание устройства (формат, движок, экраны).

## Цель

Бесплатный инструмент для интерактивных уроков: викторины, опросы, игровые задания. Без рекламы, регистрации,
аккаунтов и сохранения данных об учениках. Не заменяет iSpring целиком (нет озвучки, записи голоса, отчётов
по ученикам, редактора слайдов), но закрывает его основную часть — тесты и интерактивные задания — и добавляет
то, чего у iSpring нет: живую игру на весь класс (как Kahoot) и файлы, которые пишет нейросеть.

Автор: «хочу сделать свои уроки лучше и легче»; «нужен нативный редактор, обязательно»; формальные баллы
за iSpring цели не определяют.

## Главные решения

1. **Deixis читает данные, а не произвольный HTML.** Урок — файл (JSON): вопросы, варианты, правильные ответы,
   таймеры, картинки, тема. Показывает его сам Deixis своим плеером. Любой файл от человека или нейросети
   открывается одинаково и безопасен для телефонов зрителей. Песочница для HTML-слайда с малым API —
   возможное расширение позже, не первый этап.
2. **Один формат — три способа проиграть:** (а) самостоятельный плеер без ведущего, (б) живая игра в зале
   с ведущим, (в) экспорт SCORM 1.2/2004 для LMS (по необходимости, поздно).
3. **Редактор — нативный**, в общем коде пульта `pult/` (Compose; телефон, планшет, компьютер), отдельным
   модулем, а не внутри `Controller.kt`. Файл от нейросети открывается в редакторе, редактор пишет тот же JSON.
4. **Для нейросетей — отдельный документ** (формат, примеры, правила оформления), который можно отдать
   любой модели; проверка файла (валидатор) в `core`.
5. **Движок игры живёт на приёмнике** (ТВ, компьютер), не на пульте: сбой пульта не трогает игру
   (правило «сбой пульта не трогает вывод»). `QuizContent` — новый `Content` по образцу `CountdownContent`.
6. **Данных об учениках нет:** имена игроков только в памяти приёмника на время игры. Результаты в LMS
   (если будет SCORM) хранит сама LMS.

## Порядок работы

Принцип: экраны сначала на прототипе (правило проекта: DESIGN.md → SCREENS.md → `prototype/`), всё остальное
сразу кодом. Первым делом — **тонкий срез от начала до конца**: файл с тремя вопросами открывается
в плеере, проходится, показывает итог.

| Шаг | Что | Заметки |
|---|---|---|
| 1 ✅ | Формат, этот документ, документ для нейросетей, валидатор в `core` — готово: [../quiz/FORMAT.md](../quiz/FORMAT.md), [../quiz/FOR_AI.md](../quiz/FOR_AI.md), пример, `QuizValidator` | формат с запасом: типы вопросов, ветвление, баллы, чтобы расширение не ломало старые файлы |
| 1′ | Прототип экранов (параллельно с 1): список вопросов, форма вопроса, предпросмотр, экран ведущего, экран игрока | только 3 типа: один ответ, несколько ответов, верно/неверно |
| 2 (частично) | Модель вопроса и отрисовка в `core` + самостоятельный плеер | сделано: модель, `grade()`, `QuizRun`; осталось: `QuizContent` и отрисовка в выводе, плеер на экране |
| 3 | Редактор в `pult/` | после того как прототип устроил автора |
| 4 | Живая игра в зале: движок, страница игрока `/play`, зал, кнопки ведущего | см. «Живая игра» |
| 5 | Остальные типы (пропуски, порядок, сопоставление, ввод, опрос, облако слов), переподключение, нагрузка 30–60 телефонов | типы сразу и в редакторе |
| 6 | Экспорт SCORM — только если понадобится LMS | открытый стандарт: zip с манифестом и вызовами JS |

## Живая игра: что известно об устройстве

Что уже есть: приёмник (Ktor) отдаёт `/view` и держит WebSocket со зрителями ([../../ARCHITECTURE.md](../../ARCHITECTURE.md),
«Зрители в браузере»; [PROTOCOL.md](PROTOCOL.md) §5.5); работает по локальной сети без интернета; ключ зрителя
переживает перезапуск.

Что придётся построить:
- **Страница игрока `/play`** с двусторонним каналом (имя, ответ, свои очки). Сегодняшний `/view` только смотрит,
  кадры от браузера игнорируются.
- **Движок** в `core`: вопрос открыт → ответы собраны → результат → таблица; очки по скорости; повторный вход
  по токену после обрыва.
- **Зал в каждом выводе** (Android/ТВ, компьютер, браузерный экран). Самое дорогое. Решение ещё не принято:
  три отрисовки или одна общая (HTML во встроенном браузере). Выбираем перед шагом 4; в любом случае сверять
  снимками, чтобы «как в редакторе» совпадало с залом.
- **Кнопки ведущего** в `pult/` и `remote.html`; новые сообщения протокола.
- **Предел игроков.** Зрителей сейчас не больше 32 (`1013 too many viewers`), для класса нужно около 60,
  отдельно от зрителей трансляции.

Риски:
- **Wi-Fi с изоляцией клиентов** (школы): телефоны не видят приёмник. Запасные пути: точка доступа на телефоне
  или ноутбуке ведущего; адрес по IP, а не `.local` (на Android `.local` ненадёжен). Описать в документации.
- **Честность:** правильный ответ не уходит на телефон игрока до открытия результата.
- **Нагрузка:** 30 ответов в одну секунду на слабом ТВ-боксе — проверить в шаге 5.
- **Правила проекта:** строки интерфейса на трёх языках (содержимое урока — на языке автора); цвета и размеры
  только из токенов; новый жест — в карту жестов DESIGN.md; пульт не трогает вывод.
