# Знания и разборы: что уже выяснено, почему код устроен так, что ещё открыто

Этот файл — память проекта. В нём то, чего нет в коде: найденные причины сбоев, проверенные и отвергнутые
пути, обходные приёмы и открытые вопросы. Прежде чем чинить «странное» место, найдите его здесь: возможно,
странность — это и есть исправление.

Короткие решения с датами — в [../../DECISIONS.md](../../DECISIONS.md), изменения по версиям —
в [../../CHANGELOG.md](../../CHANGELOG.md). Здесь — подробности, которые туда не помещаются.

## 1. Разборы сбоев (причина → исправление → как не сломать снова)

### 1.1. Android-экран: шифрованный вход закрывал соединение (0.10.22–0.10.32, исправлено в 0.10.33)
- **Признак.** TLS-рукопожатие с экраном на Android проходило, после запроса — «Empty reply from server».
  Так было и в сборке с R8, и без неё.
- **Причина.** `TlsGateway` (core `Tls.kt`) расшифровывает поток и пересылает его на внутренний вход сервера.
  Внутренний коннектор Ktor слушает `127.0.0.1` (core `Receiver.kt`, второй `connector`). Шлюз шёл на
  `InetAddress.getLoopbackAddress()`, а на Android это `::1` (IPv6): соединение отклонялось, шлюз закрывал TLS.
  На компьютере (JVM) это `127.0.0.1`, поэтому тесты JVM ошибку не видели.
- **Следствие.** С 0.10.22 пульт после PIN переходит только на шифрованный вход (`SenderClient.adopt`), без
  отката на HTTP. Значит, телефон не мог работать с Android-экраном (ТВ, «Стать экраном»).
- **Исправление.** Шлюз идёт на явный `127.0.0.1` (`TlsGateway.INNER_HOST`).
- **Страховка.** Проверка на эмуляторе `tools/android-smoke.sh` → `net_check`: `/info` по HTTP и по
  TLS-порту через `adb forward`. Она и нашла ошибку.
- **Правило.** Никогда не использовать `getLoopbackAddress()` и `localhost` для связи между своими
  сокетами: только явный `127.0.0.1`, такой же, как у слушающей стороны.

### 1.2. Виртуальный монитор на Windows не создавался у автора (0.10.30–0.10.33, главная причина исправлена в 0.10.34)
Цепочка причин, найденных по журналу автора:
1. **Роль.** Автосоздание работает только у «Пульта и экрана» (`autoVirtualHall`). В роли «Пульт» его нет
   (журнал: `virtual: сам не создаю: роль …`). Вручную — «Устройства» → «Входы» → «Создать виртуальный экран».
2. **Окно прав могло остаться без ответа.** Окно UAC могло оказаться под другими окнами. Раньше любая
   неудача навсегда ставила флаг `virtual-auto-off`. Теперь флаг ставится только на явный отказ
   (код 1223 / `WindowsVirtualScreen.DECLINED`) или «Убрать». Тайм-аут окна прав → ждём монитор ещё 60 с
   (`LATE_MS`).
3. **Повторные окна прав.** Нажатия «Создать» во время ожидания вставали в очередь, и окно UAC выскакивало
   раз за разом. Теперь в `VirtualScreen.create` одна попытка за раз и пауза 5 с после неудачи; кнопка
   в пульте не нажимается, пока идёт выбор.
4. **Код 2 у помощника `deixis-display.exe`.** Windows не дала добавить сертификат драйвера в «Доверенные
   корневые» или «Доверенные издатели». Вероятно, это антивирус: на машине CI сертификат принимается.
   Теперь помощник **не останавливается**: ставит драйвер дальше, и Windows сама спрашивает, доверять ли
   издателю. Каждый шаг с текстом ошибки Windows пишется в файл (`--log <файл>`), Deixis переносит его
   в свой журнал строками `virtual: Windows: …`.
5. **Кракозябры в журнале помощника.** `cl` читал исходник как ANSI. Теперь сборка идёт с `/utf-8`
   (`windows-display/build.ps1`).
6. **Главная причина: путь с пробелом резался на части (0.10.30–0.10.33).** Deixis ставится в
   `C:\Program Files\Deixis`. Запуск помощника с правами шёл так: `powershell -Command "… -ArgumentList '"путь"' …"`.
   Java не экранирует кавычки внутри аргумента, PowerShell их выбрасывает, а `Start-Process` склеивает список
   аргументов через пробел без кавычек. Помощник получал `install C:\Program Files\…inf …`: сертификат
   «не открывался» (отсюда код 2, который приняли за антивирус), а кусок `C:\Program` становился id устройства —
   в «Диспетчере устройств» оставались битые видеоадаптеры без драйвера.
   **Исправление:** скрипт идёт через `-EncodedCommand` (Base64, UTF-16LE), аргументы помощнику — одной строкой,
   каждый в кавычках по правилам Windows (`WindowsVirtualScreen.winArg`, тест `WindowsElevateTest`). Помощник
   проверяет, что файл драйвера на месте (код 6), и при установке убирает битые устройства прошлых попыток
   (id начинается с буквы диска).
   **Почему CI не видел:** `desktop-smoke` запускал программу из `out\Deixis` — без пробела, а `windows-display.yml`
   вызывает помощника напрямую, без PowerShell. Теперь `desktop-smoke` запускает её из `…\Program Files\Deixis`.
- **Правило.** Аргументы в другую программу через PowerShell — только `-EncodedCommand`; пути в проверках CI —
  с пробелом, как у настоящей установки.
- **Статус.** На машине CI (windows-2022, админ) монитор ставится и виден (`desktop-smoke`: мониторов ≥ 2,
  путь с пробелом). На компьютере автора после 0.10.34 результат **ещё не подтверждён**.
- **Как разбирать.** Журнал автора: «Настройки» → «Диагностика» → «Отправить файлом», строки `virtual`.
  Коды помощника: 0 — готово, 2 — драйверу не доверились (сертификат не принят и установка без него
  не прошла), 3 — устройство не заведено, 4 — драйвер не встал, 6 — нет файла драйвера (путь пришёл не целым), 1223 — отказ в окне Windows.

### 1.3. Linux: проектор-«повтор» считался вторым монитором; виртуальный монитор не был виден системе (0.10.31)
- Когда проектор повторяет рабочий стол, X11 отдаёт два монитора в одной точке. Deixis выводил зал на
  «второй» монитор, то есть закрывал рабочий стол оператора. Теперь мониторы с общим левым верхним углом
  считаются одним (`withoutMirrors`, desktop `Monitors.kt`).
- Монитор через `xrandr --fb` + `--setmonitor` не виден в настройках экранов Cinnamon. Сначала теперь
  включается **свободный выход видеокарты** (HDMI или DP без кабеля, `VIRTUAL*` у драйвера Intel) в режиме
  1920×1080 (`LinuxVirtualScreen.viaOutput`). Такой монитор — настоящий для системы. Старый путь остался
  запасным.
- Монитор убирается при любом выходе, в том числе по сигналу (`shutdown()` → `VirtualScreen.releaseOnExit()`
  первым делом).
- **Как проверять без железа.** Xorg с драйвером-заглушкой (`tools/smoke/xorg-dummy.conf`): DUMMY0 —
  «ноутбук», DUMMY1…15 — свободные выходы; повтор проектора — `xrandr --output DUMMY1 --mode 1920x1080
  --pos 0x0`. То же делает `desktop-smoke` (Linux).

### 1.4. macOS: запуск вставал после первой строки журнала (0.10.30)
- В `desktop-smoke` на macOS журнал содержал только первую строку, пульт не открывался. Различие с
  предыдущей рабочей версией: объявление в сети (JmDNS) шло в основном потоке до открытия окон.
- **Исправление.** `Discovery.advertise` — в фоне. Зал и пульт не ждут сети. На неудачу проверка
  на Маке печатает `jstack` всех потоков.
- Точная причина (какой вызов JmDNS ждал) не установлена: после переноса в фон сбой не повторялся.

### 1.5. Пульт компьютера не открывался второй раз (0.10.30)
- Пульт компьютера связан со своим экраном по 127.0.0.1 токеном «Этот компьютер». Раньше он переходил на
  шифрованный вход, а токен, прошедший по TLS, становится «только по TLS». Повторный запуск программы
  просит открыть пульт через `/api/activate` (только loopback и HTTP) и получал 403.
- **Исправление.** Флаг `SenderClient.sameDevice`: со своим экраном связь без TLS. Первая попытка
  исключала loopback по адресу и сломала `SecureLinkTest`, поэтому выбран флаг.
- Ещё: токен «Этот компьютер» создаётся сразу при запуске (`operatorToken()`), иначе в роли «Экран»
  повторный запуск не мог открыть пульт. Журнал в файл пишет только запустившаяся копия
  (`Log.toFile` после привязки порта), чтобы вторая копия не переименовывала журнал первой.

### 1.6. Окно пульта на Windows оставалось под окном зала (0.10.28–0.10.29)
- На одном мониторе окно зала во весь экран закрывало новое окно пульта. `PultWindow.raise()` ставит
  пульт поверх всех на 600 мс (`RAISE_MS`), потом окно становится обычным. Пульт открывается при запуске
  всегда, когда есть монитор не под залом.

## 2. Почему так (неочевидные решения в коде)

- **Пульт ↔ свой экран компьютера без TLS** (`sameDevice`) — см. 1.5. Трафик не выходит из машины.
- **Объявление mDNS в фоне** — см. 1.4.
- **R8 только с `-dontobfuscate` и широкими `-keep`** (`android/proguard-deixis.pro`). Отражение (Ktor
  находит движки и плагины, kotlinx.serialization), JNI (VLC) и загрузка по имени (BouncyCastle) ломаются
  молча, только при подключении. Читаемые журналы ошибок важнее нескольких мегабайт. Выигрыш — оптимизация
  Compose и −8 % APK. Без проверки сети на эмуляторе (`net_check`) R8 не включать заново после правок.
- **Мониторы-повторы = один монитор** — см. 1.3. Настоящие соседние мониторы не начинаются в одной точке.
- **Неудача автосоздания виртуального монитора не запоминается**, кроме явного отказа — см. 1.2.
- **`connectCard` — флаг состояния, а не новое сообщение протокола.** Старые экраны не знают нового типа
  `Msg`. HTTP-эндпоинт `/api/connect-card` у старого экрана отвечает 404, пульт говорит «обновите Deixis».
  Новый `Show` сбрасывает флаг: `ReceiverState` создаётся заново.
- **«Наложение» — отдельная раскладка, а «Титры» не переделаны.** Титры на чёрном нужны проектору поверх
  сцены. Видео и трансляция в наложение не идут: под окном и так картинка монитора.
- **Прозрачность окна «Наложения»** берётся, только если система её умеет
  (`isWindowTranslucencySupported`). Иначе окно на чёрном, как «Титры», и предупреждение `overlay` в журнале.
- **Общий кэш PDF (`PdfPages`)** — один на процесс: два монитора и зрители не рисуют одну страницу дважды.
  Документ закрывается после 60 с простоя, потому что на Windows открытый файл нельзя удалить.
- **Библиотека пульта читается вне потока интерфейса**: на телефоне — при старте процесса
  (`PhoneApp.onCreate`), на компьютере — в IO до открытия окна (`ReceiverApp.pultController()`).
- **Стихи готовятся заранее** (`Controller.warmScripture`) после загрузки модулей Библии.

### 3.1. Найдено при сверке документации с кодом (2026-11-12), не исправлено
Каждый пункт — из чтения кода; подтверждения на устройстве нет, если не сказано иное. Приоритет — по риску для показа.

| Риск | Что | Где |

## 4. Как проверять то, чего нет под рукой

| Что | Как |
|---|---|
| Android целиком | только эмулятор в CI (`smoke.yml`, `release.yml`); локально KVM нет |
| Windows, macOS | `desktop-smoke.yml`, GUI-тесты в `ci.yml` (Windows, macOS, Linux) |
| Виртуальный монитор Linux | Xorg-заглушка (раздел 1.3) — работает и локально |
| Виртуальный монитор Windows | `windows-display.yml` (драйвер), `desktop-smoke.yml` (программа) |
| Окна на Linux | `xvfb-run` + `openbox` + `wmctrl`/`xdotool` |
| Зависание при запуске | `jstack <pid>`; на Маке CI печатает потоки сам |
| Журнал пользователя | «Настройки» → «Диагностика» → «Отправить файлом» (отчёт + log.txt всех экранов) |

Артефакты GitHub Actions (снимки, журналы) из облачной среды разработки скачать нельзя: прокси не пускает
к хранилищу артефактов. Логи заданий читаются через API GitHub (`get_job_logs`), поэтому важное
печатается прямо в лог задания.
